homerun the demowrite-up

Write-up

1. The scene in 1997

SAINT was released at Assembly 1997 (Helsinki) by halcyon and the tracker group da jormas. Code by blitz, graphics by shrine, placidity and croaker, meshes by ren, music by naks, pam and vesuri (“3 tunes mixed to 1”). In 1997 a PC demo meant: MS-DOS, a 386/Pentium, VGA mode 13h (320×200, 256 colours from an 18-bit palette), a Sound Blaster, and a 32-bit DOS extender (here PMODE) to escape the 640 KB real-mode limit. No GPU: every pixel is written by the CPU, so effects are built from lookup tables and tricks — precomputed maps, palette games and bilinear interpolation — rather than brute force.

2. How the EXE is built

The 2.5 MB file starts with a tiny real-mode Blinker-style stub that re-opens the EXE, loads a PMODE protected-mode program and its data (almost uncompressed), then switches to 32-bit mode. The program contains three main loops — one per “part” — plus the intro and a software mixer-driven S3M player (by asmu). Images are ColoRIX RIX3 files (raw 6-bit VGA palette + pixels); the soundtrack is a plain Scream Tracker 3 module.

3. The engine: “halcyon super kolmedee enkine”

Every frame of a part does the same thing:

  1. Camera. A cubic (Catmull-Rom/Hermite) spline is evaluated through a table of keyframes (10 floats each: position, angles…), advanced a little every timer tick.
  2. Tunnel grid. 41×26 grid vertices (one per 8×8 screen block) are rotated by the camera matrix and passed to a warp function. The warp casts the ray camera→vertex against an analytic surface (a cylinder, solved as a quadratic: t = −(b+√(b²−4ac))/2a) and returns three numbers: texture u (angle, via atan2), texture v (position along the tube) and a depth shade. Several variants exist (with/without a sinusoidal wobble); a hidden key toggles them.
  3. Interpolated raster. Instead of ray-casting 64 000 pixels, the (u,v,shade) triples are bilinearly interpolated across each 8×8 block in fixed point. Each pixel then costs two table lookups: t = texture[v][u] and colour = shade_table[shade][t] — the second table is the “quantized shading tables” built during the loading screen, so the palette gets darker/foggier with depth without any per-pixel arithmetic.
  4. Objects. A depth-sorted list (key = z) of sprites, billboards, flares and clipped flat/textured triangles is drawn over the tunnel.
  5. Palette. The timer ISR cross-fades between three stored palettes through the DAC (out 3C8h/3C9h), which gives the white flashes and fades between scenes without touching the pixels.

4. Timeline

The demo's clock is the music: the player writes the current S3M order into a variable that every part tests (cmp word [12BFh], n). Intro = orders 0–2, part 1 = 3–5, part 2 = 6–11, part 3 = 12–21, D = 22–23, A = 24–25, B = 26–27, E = 28–34, F = 35–38, C = 39–44 (the whole module, ≈ 4 min 22), followed by a full-screen picture shown for 700 ticks in silence. Rows matter too: parts fade or switch on (order,row) thresholds, and the module changes speed between sections (orders 12–27 are 64 rows of 55 ms, the others about 110 ms), so the runner uses the real start time of every row (tools/s3m_timeline.py → row_times.json). The browser runner uses libopenmpt for the same module and maps music time to these scenes.

4b. Two things that make the crystals special

The glassy crystals of part 1 are not lit polygons. Each triangle is rasterised by 0x1FC7B, which does not write colours at all: every pixel it covers is replaced by table[level][pixel], a 64×256 table that brightens and tints the existing colour. The “level” is how squarely the face looks at the camera, reduced with distance. The glows around them are 256-pixel-wide sprites selected by distance (a small mip chain) and blitted through the same table, so light adds up without any real alpha blending.

And the world is tick-driven: the 70 Hz retrace interrupt advances every animation variable (camera spline parameter, wobble phases, crystal spins, palette fades); the main loop only draws whatever the state is. That is why the demo runs the same at any frame rate — and why the port can seek by replaying ticks.

4c. The 3D scenes: vertices and triangles

Part 1 contains 33 crystals. Each is a small mesh of 20 vertices and 36 triangles generated at load time (that is the “loading and preparing scene…” step), so 660 vertices and 1 188 triangles in total. Part 2's morphing star is one object of 105 vertices and 206 triangles whose vertices are interpolated between two stored shapes every frame. Records are plain arrays:

vertex (0x40 bytes)  +04 flag (1 = not needed)   +08 x,y,z model space (float32)
                     +14 sx  +18 sy  +1C z_view  +20 1/z   (after transform/projection)
                     +00 outcode (y<0, y>200, x<0, x>320)   +30.. u,v,intensity (textured meshes)
face   (0x30 bytes)  +00 draw handler  +04 raster routine  +08 culled flag
                     +0C,+10,+14 pointers to the 3 vertices
                     +18..+24 plane equation  n·p + d   +2C level / shade

Per frame and per object the engine runs a fixed pipeline: (1) frustum-cull the object's bounding sphere; (2) put the eye in object space and test every face's plane equation (back-face culling — about 1 000 of the 1 188 triangles die here; 195 are drawn in the checked frame); (3) transform only the vertices of surviving faces with one 4×4 matrix (object·camera, row-vector convention); (4) perspective-project (sx = x·f/z+160, sy = y·0.83f/z+100, keep 1/z) and compute a 4-bit outcode per vertex; (5) push (65535 − depth key, face) on a list; (6) a two-pass radix sort (low byte, then high byte of the 16-bit key) orders the list back to front (no z-buffer); (7) each face goes to its handler, which clips against the screen with four Sutherland–Hodgman passes only if an outcode is non-zero, fans the polygon into triangles and calls the raster routine.

4d. Inner loops

All the speed is in a handful of loops. Everything is integer or table based; there is no division and no multiplication per pixel.

Tunnel, one pixel (8 of these are unrolled per block row, two pixels packed into one 16-bit store). si/ch/dh hold the interpolated v/u/shade in 16.8 fixed point; the texture is 256×256 so the “address calculation” is just placing bytes into ax:

mov  ax, si              ; ah = v           (al is overwritten next)
mov  al, ch              ; al = u           -> eax = base | v<<8 | u
add  ecx, [dU]           ; step u
add  esi, [dV]           ; step v
mov  al, [eax]           ; texel (a quantised colour id)
mov  ah, dh              ; ah = depth shade -> eax = shade<<8 | texel
add  edx, [dZ]           ; step shade
mov  bl, [eax+10000h]    ; final palette index: 64 KB shading table

Filter triangle span (crystals; the whole “translucency” is a table lookup per covered pixel; ah holds the face level, set once per triangle):

L: mov  al, [edi]        ; pixel already on screen
   inc  edi
   dec  ecx
   mov  al, [eax]        ; table[level][pixel]
   mov  [edi-1], al
   jne  L

Glow sprite (flares; the sprite's own value picks the table row, the pixel underneath picks the column, so the glow adds light):

L: mov  al, bh           ; u (integer part of the 16.8 coordinate)
   inc  edi
   add  ebx, [step]
   mov  dl, [edi]        ; destination pixel   -> edx = table | row | pixel
   mov  dh, [eax+sprite] ; sprite intensity    -> picks the table row
   dec  esi
   mov  al, [edx]        ; remapped colour
   mov  [edi], al
   jne  L

Palette cross-fade (runs in the retrace interrupt over all 768 DAC values: two linear interpolations between three palettes, which is how the whole screen pulses and flashes to white without touching a pixel):

L: mov  al, [esi+palA]  ; xor/mov bl,[palB] / mov cl,[palC] omitted
   sub  eax, ebx
   imul eax, edi         ; edi = A/B mix 0..1023
   sar  eax, 10
   add  eax, ebx
   sub  eax, ecx
   imul eax, ebp         ; ebp = fade to C (white) 0..1023
   sar  eax, 10
   add  eax, ecx
   out  dx, al           ; DAC data port 3C9h
   inc  esi
   jne  L

Cost check for the tunnel: a 320×200 frame is 1 040 grid vertices through a ray cast (floating point, the only expensive part), then 64 000 pixels × 8 simple instructions ≈ 0.5 M integer instructions — fine for a Pentium at 20+ fps in 1997.

4e. The last scenes

Intro (orders 0–2). A 160×100, 4-bit footage of 142 frames at 10 fps. Each frame is a run-length stream of nibbles (F0 cn = run of n pixels of colour c) that is written in 4×4 tiles (a cache-friendly layout), doubled to 320×200 with linear interpolation, then smeared: two recursive passes, one forward one backward, blend every pixel with its up-right (resp. down-left) neighbour using a radial 8-bit alpha mask, via two multiplication tables (h·l and (255−h)·l). The result is a soft vignette: sharp in the middle, streaky at the edges. The “da HALCYON / da JORMAS” logos are copied over it (top half from order 1 row 60, all of it in order 2), and the last rows flash to white.

D (orders 22–23). No 3D at all: a 41×26 grid of (u,v,shade) is computed every frame from two orbiting “centres”: the distance to both is summed, turned into an angle and a zoom, and rotates/scales the (x,y) coordinates; the grid then goes through the same 8×8 interpolation as the tunnels. Text sprites follow a table of (order,row) triggers. The picture shown at frame n uses the grid computed at frame n−1.

E (orders 28–34). A textured sphere whose vertices are rotated in place every frame and clamped into a 200-unit box: as the sphere's position wanders on a Lissajous curve it is flattened against the walls of an invisible cube, and the damage is cumulative. A 168-line grid cage shows the box. The bull is a 118×200 sprite stamped in a corner (two poses alternating every 4 rows); the palette flashes with a sine-driven blend.

F (orders 35–38). A cave (193 vertices) lit by a single point light at the origin — the glowing 79-vertex star that rotates there — with the camera flying along a spline; the vertical field of view pulses. A faces whose three vertices receive no light are filled with colour 0. At the end a 1-bit, 216×158 animation (22 frames) of a silhouette is stamped on top.

C (orders 39–44). A plane tunnel (z = −300) that melts into a sphere after about 15 s, a big textured gem (310 vertices) with five pentagonal stars, 36 spinning shards (6 vertices each, rotating at slightly different speeds), a billboard figure whose sprite is selected from a 40-view sheet by the viewing angle, and the “dancer” strip on the right. When the module ends the program copies a 320×200 picture to the screen and waits 700 ticks.

5. Method

Static analysis alone is slow, so the reverse used emulation as an oracle: DOSBox-X to run the demo and dump RAM, then a Unicorn-based harness (tools/oracle.py) that runs the demo's own frame loop from any snapshot, giving bit-exact reference frames to diff the JavaScript port against. The full log is in docs/PROCESS.md.
